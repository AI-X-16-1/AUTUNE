# Database Migrations

## The problem this solves

With a single linear Alembic history, two people generating a migration on the
same day produce two revisions with the same `down_revision`. Every merge
becomes a conflict, and resolving it by hand is where migration histories go
wrong.

Each module gets an **independent Alembic branch**. Five people generate five
migrations on the same day and nothing conflicts.

Shared entities in `packages/core` are a sixth branch, migrated separately.

## Configuration

```ini
# infra/alembic.ini
[alembic]
version_locations = packages/core/migrations
                    modules/audio/migrations
                    modules/extraction/migrations
                    modules/gap/migrations
                    modules/context/migrations
                    modules/intelligence/migrations
```

## Creating your branch (once, in W1)

Your module's first revision starts a new root:

```python
revision = "a1b2c3d4e5f6"
down_revision = None
branch_labels = ("gap",)
depends_on = None
```

- `down_revision = None` — this is a root, not a continuation
- `branch_labels = ("<module>",)` — names the branch
- Both are set exactly once per module, on the first revision only

## Daily use

**Generate:**

```bash
uv run alembic -c infra/alembic.ini revision --autogenerate \
  -m "add gap_topics table" \
  --head gap@head \
  --version-path modules/gap/migrations
```

**Apply all branches:**

```bash
uv run alembic -c infra/alembic.ini upgrade heads
```

`heads`, plural. `upgrade head` fails with multiple branches — that error means
you typed the singular.

**Inspect:**

```bash
uv run alembic -c infra/alembic.ini heads      # one head per branch
uv run alembic -c infra/alembic.ini history    # full graph
uv run alembic -c infra/alembic.ini current    # what is applied
```

**Roll back your branch only:**

```bash
uv run alembic -c infra/alembic.ini downgrade gap@-1
```

## Rules

1. **Never edit another module's migration file.** Not to fix a typo, not to
   resolve a conflict.
2. **Never touch a table you do not own** in a migration — including shared
   entities, which belong to `packages/core`.
3. **Always check the autogenerated output.** Autogenerate sees the full
   metadata and will happily emit DDL for tables it thinks are missing. Delete
   every operation that is not about your own prefixed tables before committing.
4. **Table prefix is mandatory.** `gap_topics`, not `topics`.
5. **No cross-module foreign keys.** They create an ordering dependency between
   independent branches. See `../architecture/data-model.md`.
6. **Write the downgrade.** An empty `downgrade()` is not acceptable.
7. **One logical change per revision.** Do not batch a week of schema work into
   one file.

## Ordering against the core branch

`alembic upgrade heads` applies every branch, but it does **not** order one
branch against another. A module revision that references anything the `core`
branch creates — a foreign key to a shared entity, or a type from an extension —
can run before `core` has caught up, and fails on a clean database (which is
what CI starts from).

Pin it with `depends_on` on the **first** revision that needs it; the rest of
your branch chains onto that one and inherits the ordering.

| Your revision uses… | `depends_on` |
| --- | --- |
| A foreign key to `meetings`, `teams`, `users`, … | `"d34994600a9a"` (core: shared_entities) |
| A `vector` column (pgvector) | `"aad0ea392ddc"` (core: enable_pgvector — chains onto shared_entities, so this covers both) |

`depends_on` couples your branch to a specific `core` revision id. Migration
history is append-only, so the id is stable. See ADR 0008.

## The autogenerate trap

Autogenerate compares full model metadata against the live database. If your
local database is missing another module's tables, it will generate
`create_table` for them inside *your* migration. That migration then runs in CI
and production and creates tables you do not own, with a revision chain that
does not belong to them.

Always run `upgrade heads` before generating, and always read the diff.

## Adding a column to a shared entity

`meetings`, `utterances`, and the rest belong to `packages/core`. To add
something:

1. Open an issue — other modules read these tables, and the answer should
   outlive the conversation.
2. The change is made in `packages/core`, on the `core` branch.
3. It goes through a pull request with team review.

Do not add a column to `utterances` from a module migration. Put module-specific
state in your own prefixed table with a foreign key to `utterances.id`.

## Deletion paths

Every table you create must be removable when a meeting or a user is deleted
(`../architecture/privacy.md`).

- Prefer `ForeignKey("meetings.id", ondelete="CASCADE")`, which handles it for
  free.
- If your table cannot cascade, register a deletion hook in `autune_core` and
  cover it with a test.

A table with no deletion path is a compliance defect, and it is caught in
review.

## Conflicts

If two revisions on the same branch end up with the same `down_revision` — which
should only happen within one module — merge them:

```bash
uv run alembic -c infra/alembic.ini merge -m "merge gap branch" <rev1> <rev2>
```

If revisions across *different* branches appear to conflict, something is wrong
with the branch setup. Do not merge branches; ask before proceeding.

## CI

CI runs `upgrade heads` against a clean database, then `downgrade` and
`upgrade` again. A migration that cannot round-trip does not merge.
